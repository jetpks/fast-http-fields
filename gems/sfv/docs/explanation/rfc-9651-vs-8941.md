# RFC 9651 vs RFC 8941

RFC 9651 obsoletes RFC 8941, the original Structured Field Values
specification. fast-sfv implements RFC 9651; RFC 8941 is the
documented subset — everything an 8941 field can say, a 9651 parser
reads, and the two RFC 9651 additions are what an 8941 implementation
cannot. This page is what changed and where the gem stands in it.

## What changed — Appendix D's own inventory

RFC 9651 Appendix D lists the changes from RFC 8941 verbatim:

- Added the Date Structured Type (Section 3.3.7).
- Stopped encouraging use of ABNF in definitions of new Structured
  Fields (Section 2).
- Moved ABNF to an informative appendix (Appendix C).
- Added a "Structured Type" column to the HTTP Field Name Registry
  (Section 5).
- Refined parse failure handling (Section 4.2).
- Added the Display String Structured Type (Section 3.3.8).

Of the six, two are user-visible new types — Date (§3.3.7, an
integer delta-seconds from 1970-01-01T00:00:00Z with a leading `@`)
and Display String (§3.3.8, a percent-encoded string that may carry
non-ASCII content with a leading `%`). The other four are
specification-craft changes: ABNF is no longer encouraged for
defining new fields and moved to informative Appendix C, the field
name registry now records whether a field is an Item, List or
Dictionary, and the §4.2 parse failure handling is refined.

## Backward compatibility — §2.4

RFC 9651 §2.4 states the compatibility rule in both directions:

- Forward: a field whose definition references RFC 9651 may use Date
  and Display String; a field whose definition references RFC 8941
  cannot — an RFC 8941 implementation treats those values as invalid
  and discards them.
- Backward: "this document is designed to be backward compatible with
  RFC 8941; a parser that implements the requirements here can also
  parse valid Structured Fields whose definitions reference RFC 8941."

One nuance the same section carries: upgrading a parser to a newer
revision can make a previously-invalid field value valid — a field
instance carrying a Date where the field's 8941-era definition does
not accommodate Dates fails under an 8941 parser and parses under a
9651 one.

## Where the gem stands

fast-sfv implements RFC 9651 — both new types parse and serialize
today, and the 8941 subset comes along for free, because every 8941
field value is a valid 9651 field value of the same shape:

```ruby
Fast::SFV.parse_item("@1659578233").value.value # => 1659578233
Fast::SFV.parse_item("%\"f%c3%bc\"").value.value # => "fü"
Fast::SFV.serialize_item(Fast::SFV::Item.new(Fast::SFV::Date.new(1659578233), {})) # => "@1659578233"
Fast::SFV.serialize_item(Fast::SFV::Item.new(Fast::SFV::DisplayString.new("fü"), {})) # => "%\"f%c3%bc\""
```

The conformance corpus carries both RFCs' records, so the 8941 subset
is pinned by the same tests as the 9651 additions.

## starry, and the benchmark's compared surface

starry, the RFC 8941 reference implementation fast-sfv's benchmark
compares against, is an 8941 implementation — which is exactly why
the benchmark's compared surface is the RFC 8941 subset both
libraries implement: the three parse entry points and the three emit
entry points over the eight 8941 types. Date and Display String are
outside that surface, not because they are unmeasured but because
starry has no position on them. See
[Performance and allocations](performance.md).

The one deliberate divergence on the shared surface is the token
mapping: starry answers Symbols, fast-sfv answers
`Fast::SFV::Token`. The divergence and its rationale are in
[Design decisions in fast-sfv](design-decisions.md).
